# ESP32-C5 Configuration

This document sets out how the ESP32-C5 is configured as the root of trust: eFuses, boot chain, TEE, flash partitions and anti-rollback.
Facts about the chip come from ESP-IDF's C5 support files (`soc_caps.h`, `esp_efuse_table.csv`, the ESP-TEE component) and Espressif's documentation
as of November 2026. eFuses cannot be changed once burned, so every setting here must be confirmed on real parts first (`doc/questions.md`).

## Part

**ESP32-C5HR8**: 240 MHz RISC-V, 384 KB SRAM, 8 MB PSRAM in the package, no flash in the package.

The HR8's flash is an external part, so its pins can be probed (R2, R6). The ESP32-C5HF4 has 4 MB of flash in the package but no PSRAM,
which is the configuration Espressif recommends against probing. The HR8 is chosen for its PSRAM, and the exposure is recorded as a known risk.

Security hardware used: secure boot v2, XTS-AES flash and PSRAM encryption with pseudo-rounds against power analysis, SHA, HMAC, AES and RSA accelerators,
TRNG, the access permission manager (APM) and PMP for the TEE, and glitch detectors (named in Espressif advisory AR2023-007 as present on the C5).

## eFuse key blocks

The C5 has six 256-bit key blocks. Each has a purpose field that limits which hardware can use it.

| Block | Purpose | Contents | Source | Software can read |
|---|---|---|---|:-:|
| KEY0 | SECURE_BOOT_DIGEST0 | SHA-256 of the main RSA-3072 release key | Manufacturer | Yes (public) |
| KEY1 | SECURE_BOOT_DIGEST1 | SHA-256 of the backup RSA-3072 release key, held in a separate HSM | Manufacturer | Yes (public) |
| KEY2 | XTS_AES_128_KEY | Flash and PSRAM encryption key | Generated on chip at first boot; nobody knows it | No |
| KEY3 | HMAC_UP | **TEE storage key**: the key ESP-TEE's secure storage derives its encryption keys from | Generated on chip at first boot; nobody knows it | No |
| KEY4 | HMAC_UP | **Device root key** | HSM, at enrollment: KDF(device master, chip ID) | No |
| KEY5 | — | Spare | — | — |

Notes:

- **The third secure boot digest slot is not used.** It must be revoked at provisioning so no one can add a key to it later
  (ESP-IDF does this unless told otherwise).
- **XTS-AES-256 needs the C5's Key Manager,** which ESP-IDF currently marks as not supported on the C5 (`SOC_KEY_MANAGER_SUPPORTED 0`),
  so the base design uses XTS-AES-128 from an eFuse key. Moving to XTS-AES-256 is an open question for when the Key Manager is supported.
- **HMAC_UP keys** return their HMAC to software, which here means to the TEE alone: the TEE owns the HMAC peripheral through the APM.
  The keys themselves are read-protected and never leave the peripheral.
- **Why the device root comes from the HSM** rather than the chip: the HSM must be able to derive the same keys, so that it can issue a
  replacement host, authenticate the device to the enrollment server, and issue developer builds. The cost is that an HSM insider could too (R19).
- **KEY5** could later hold a soft-JTAG re-enable key for failure analysis of returned units, or a key-manager-related key. Leaving it
  blank keeps that option; the trade-off is in `doc/questions.md`.

## Other eFuse settings

| Setting | Value | Why |
|---|---|---|
| SECURE_BOOT_EN | 1 | Secure boot v2, RSA-3072 (ECDSA on the C5 has an erratum; Espressif recommends RSA) |
| SECURE_BOOT_AGGRESSIVE_REVOKE | 0 | Aggressive revocation can brick a unit; keys are revoked deliberately instead |
| SECURE_BOOT_KEY_REVOKE2 | 1 | Unused third digest slot |
| SPI_BOOT_CRYPT_CNT | Release mode | Flash encryption permanently on |
| XTS_DPA_PSEUDO_LEVEL, XTS_DPA_CLK_ENABLE | Highest level that meets the performance budget | Power-analysis countermeasures for flash decryption (AR2023-007) |
| DIS_PAD_JTAG, DIS_USB_JTAG | 1 | No debug access. Soft disable with an HMAC re-enable key is the alternative (KEY5) |
| DIS_DIRECT_BOOT | 1 | No booting around the bootloader |
| ENABLE_SECURITY_DOWNLOAD, or DIS_DOWNLOAD_MODE | 1 | Secure download mode allows only basic flash writes, which keeps the recovery path for bricked units; disabling it entirely is stricter (open question) |
| DIS_FORCE_DOWNLOAD | 1 | Software cannot force download mode |
| SECURE_VERSION (9 bits) | Thermometer code | Top 3 bits: TEE anti-rollback; low 6 bits: application anti-rollback |
| BOOTLOADER_ANTI_ROLLBACK_EN, secure version (4 bits) | 1 | Bootloader anti-rollback |
| RECOVERY_BOOTLOADER_FLASH_SECTOR | Set | The ROM falls back to a second bootloader if the first fails, so bootloader updates are safe |
| Write protection | All of the above, and the key purposes | So no later code can change them |

## Boot chain

1. **ROM** checks the second-stage bootloader's RSA signature against KEY0 or KEY1, and its version against the bootloader anti-rollback eFuses.
   If it fails, the ROM tries the recovery bootloader.
2. **Bootloader** checks the TEE image and the application image (RSA signature, anti-rollback version), choosing the A or B slot of each from its OTA data
   and falling back to the other slot if a check fails or a new image was not confirmed.
3. **TEE** starts in machine mode, takes ownership of the HMAC peripheral, eFuse controller, TEE flash regions and its own memory through the APM and PMP,
   and checks the application's build descriptor: a production build, or a developer build whose device ID and epoch match this device (`doc/roles.md`).
4. **Application** starts in user mode. It configures the ECP5 from the bitstream in its own image and checks it (`doc/fpga.md`), then marks the new image
   valid if this is the first boot after an update.

## TEE

ESP-TEE supports the C5 (the component lists esp32c6, esp32h2, esp32c5 and esp32c61). It provides secure storage keyed by an HMAC_UP eFuse block,
TEE OTA updates, TEE anti-rollback, attestation, and an option that routes all application flash access through the TEE so the application cannot write
TEE regions directly. That option slows flash access, which matters only during updates, so it is enabled.

**The application does the I/O.** The UART, BLE, Wi-Fi, the sensor link and the shared SPI2 bus (MicroSD card and ECP5) belong to the application.
The TEE sees only frames and records: it authenticates and decrypts what comes in, and encrypts and authenticates what goes out. The application moves
ciphertext it cannot read or forge, so it never needs to be trusted with the links, and the TEE needs no drivers for them.

**Services the TEE offers the application:**

| Service | What the application gets |
|---|---|
| User data | Read and write records on the MicroSD card, during an open host session only. Plaintext in, plaintext out; the keys stay in the TEE |
| Host session | Frames from the host link go into the TEE and come out as authenticated plaintext |
| Sensor | Pairing, sessions and authenticated readings with their age (`doc/sensor.md`) |
| Update | Hand over a package; the TEE checks, decrypts and installs it |
| Event log | Append application events; the TEE adds its own |
| Identity | A MAC over a server nonce, for the enrollment server (`doc/enrollment.md`) |
| Status | Build mode, versions, pairing state, enrollment state, and the radio policy from the build descriptor |
| CLI sessions | Authenticated, encrypted sessions over the UART or BLE, under the host key or the developer key, with attempt limits |
| Wi-Fi credentials | Stored encrypted; released to the application's Wi-Fi driver only when the radio policy allows Wi-Fi |

**Keys derived from the device root** (HMAC_UP on KEY4, inside the TEE), each with its own label:

| Key | Derivation |
|---|---|
| Identity key | HMAC(root, "identity") |
| Host key | HMAC(root, "host") |
| Data key | HMAC(root, "data"), then combined with the host's data secret in each session: HKDF(data key, host data secret) |
| Log key | HMAC(root, "log") |
| Developer key | HMAC(root, "developer" ‖ epoch) (`doc/roles.md`) |

The HSM computes the same values from its device master and the chip ID.

**Records in TEE secure storage:** the distribution key, the newest installed version of each image, the developer epoch, sensor pairings,
the sensor denylist, the enrollment record, and the head of the event log's hash chain.

## Radios

The Wi-Fi and BLE stacks run in the application, in user mode. The **radio policy** (Wi-Fi on or off, BLE on or off) is a field of the build descriptor,
covered by the release signature, so only the application owner sets it. The TEE reads it at boot, reports it, and withholds Wi-Fi credentials when Wi-Fi is off.
Whether the TEE can also deny the application access to the radio hardware through the APM, so a compromised application cannot turn on a radio
the policy disables, is an open question (`doc/questions.md`, C12).

## Flash partitions

A proposal for 16 MB of external flash. Sizes are to be confirmed from real image sizes; the bitstream for an LFE5U-25 is about 0.6 to 0.7 MB, and for an LFE5U-85 about 2.4 MB.

| Partition | Size | Contents |
|---|---|---|
| Bootloader | 64 KB | Second-stage bootloader |
| Recovery bootloader | 64 KB | The ROM's fallback bootloader |
| Partition table | 4 KB | |
| TEE OTA data | 8 KB | Which TEE slot is active |
| TEE A, TEE B | 512 KB each | TEE images |
| TEE secure storage | 64 KB | Encrypted under keys from KEY3 |
| OTA data | 8 KB | Which application slot is active, and whether it is confirmed |
| Application A, application B | 4 MB each | Application, with the ECP5 bitstream embedded |
| Event log | 256 KB | HMAC-chained entries (also copied to the card) |
| Application data (NVS, encrypted) | 64 KB | Non-secret settings |
| Reserved | rest | |

Offline update packages are staged on the MicroSD card. Over-the-air packages stream into the inactive slot: the TEE checks the signed header first,
then decrypts and writes the payload while hashing it, and marks the slot bootable only if the hash matches. An interrupted or altered download leaves
a slot that is never selected.

## Anti-rollback

Three layers, from cheapest to strongest:

1. **The TEE's version record.** The TEE refuses any package older than the newest version it has installed. Equal versions are allowed, so a damaged
   slot can be repaired. This covers everything that comes through the update path, with no limit on the number of releases.
2. **The anti-rollback eFuses.** A **security release** also advances the eFuse secure version, and the bootloader then refuses older images even if
   someone writes them back with a programmer. There are only 6 steps for the application, 3 for the TEE and 4 for the bootloader, so a release advances them only when an
   older version must never run again.
3. **Online updates.** When the device can reach the update server over Wi-Fi or through the host, the server offers only current releases (`doc/enrollment.md`).

A flash restore of a version that was not a security release is accepted (R4).
